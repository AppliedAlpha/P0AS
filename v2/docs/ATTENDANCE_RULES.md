# 출결 판단 규칙

기준: 2026-10-27의 v2 구현, `0003_attendance_revocation.sql` 적용 후. 개발용 가상 데이터로 검증했습니다. 아래는 학생 출석 폼의 학번·이름 검증부터 토큰 제출까지 이어지는 흐름입니다. 관리자 수동 조작은 마지막 절에서 따로 설명합니다.

## 변하지 않아야 하는 원칙

1. 명단에 등록된 학번과 이름이 일치해야 학생 세션을 발급합니다.
2. 현장 출석·수동 승인·과제 인정은 모두 출석한 상태입니다. 이미 출석한 학생은 다른 미사용 토큰으로도 다시 출석할 수 없습니다.
3. 미출석이고 잠기지 않은 학생만, 접수 중에 유효한 미사용 토큰으로 출석할 수 있습니다.
4. 출석 성공 시에만 토큰을 사용 처리합니다. 거절된 요청은 토큰의 기존 상태를 바꾸지 않습니다.
5. 출석 기록·토큰 사용·성공 활동 기록은 하나의 원자적 쓰기로 처리합니다. 중간 실패는 전체 취소됩니다.
6. 관리자의 미출석 처리는 출결만 취소합니다. 과거 사용 토큰은 사용 완료 상태로 남으며, 다시 출석하려면 다른 미사용 토큰이 필요합니다.

## 1. 학번과 이름

개인정보 동의, 정상 서버 설정과 요청 형식을 전제로 합니다.

| 학번 | 이름 | 결과 | 출결 | 토큰 | 토큰 실패 횟수 |
|---|---|---|---|---|---|
| 명단에 있음 | 해당 학번의 이름과 일치 | 학생 확인 통과, 다음 단계 진행 | 아직 변경 없음 | 변경 없음 | 변경 없음 |
| 명단에 있음 | 불일치 | 학생 확인 거절 | 유지 | 유지 | 증가하지 않음 |
| 명단에 없음 | 어떤 이름이든 | 학생 확인 거절 | 유지 | 유지 | 증가하지 않음 |
| 다른 학생의 학번 | 원래 학생의 이름 | 두 값이 한 명단 항목에 대응하지 않으면 거절 | 유지 | 유지 | 증가하지 않음 |
| 다른 학생의 정확한 학번 | 그 학생의 정확한 이름 | 그 학생으로 확인됨 | 이후 그 학생의 상태로 판단 | 이후 토큰 규칙 적용 | 그 학생 기준 |
| 빈 값·허용 형식 밖 학번 | 빈 값·40자 초과 이름 등 | 입력 오류 | 유지 | 유지 | 증가하지 않음 |

학번은 앞뒤 공백을 제거한 뒤 비교합니다. 4~24자의 영문·숫자·하이픈을 허용하며 대소문자와 선행 0을 구분합니다. 이름은 유니코드 NFC 정규화, 앞뒤 공백 제거, 연속 공백을 한 칸으로 정리한 뒤 대조합니다. 이름 중간의 공백을 전부 제거하거나 영문 대소문자를 무시하지는 않습니다.

이 방식은 **명단의 학번·이름 조합 확인**입니다. 다른 학생의 두 정보를 정확히 아는 사람이 그 학생으로 입력하는 것까지 구별하는 학교 SSO·신분증 인증은 없습니다. 같은 이름이 여러 명이어도 학번으로 구별합니다.

## 2. 접수 상태

학번·이름 확인을 통과하고, 정상 형식의 토큰을 제출한 경우입니다.

| 접수 상태 | 출석 시도 | 출결·토큰 상태 | 토큰 실패 횟수 | 결과 조회 |
|---|---|---|---|---|
| 시작 전 `PRE` | 거절 | 모두 유지 | 증가하지 않음 | 가능 |
| 진행 중 `OPEN` | 아래 규칙으로 판단 | 아래 표 참조 | 아래 표 참조 | 가능 |
| 종료 `CLOSED` | 거절 | 모두 유지 | 증가하지 않음 | 가능 |

학생 화면은 시작 전·종료 상태에서 출석 입력 폼을 표시하지 않습니다. 서버도 현재 접수 상태를 다시 검사하므로 화면이 열려 있는 동안 종료되어도 새 출석은 거절됩니다. 관리자의 수동·과제 승인이나 미출석 처리는 접수 종료 후에도 가능합니다.

## 3. 현재 출결과 토큰의 조합

학번·이름이 일치하고, 접수 중이며, 동의·세션·요청 제한을 통과한 경우입니다. `유효한 미사용`은 발급 기록이 있고 아직 사용되지 않은 토큰입니다.

| 현재 학생 상태 | 제출 토큰 | 결과 | 출결·점수·시각 | 토큰 결과 | 토큰 실패 횟수 |
|---|---|---|---|---|---|
| 미출석, 실패 0~2회 | 유효한 미사용 | 성공 | 현장 출석·5점·현재 시각 | 제출 토큰만 사용 완료 | 기존 값 유지 |
| 미출석, 실패 0~1회 | 이미 자신이 사용함 | 거절 | 유지 | 기존 사용 완료 유지 | +1 |
| 미출석, 실패 0~1회 | 이미 다른 학생이 사용함 | 거절 | 유지 | 기존 사용 완료 유지 | +1 |
| 미출석, 실패 0~1회 | 6자리지만 발급 기록 없음·삭제됨 | 거절 | 유지 | 생성·변경 없음 | +1 |
| 미출석, 실패 2회 | 이미 사용했거나 발급 기록 없음 | 거절 후 잠금 | 미출석 유지 | 기존 상태 유지 | 3회가 됨 |
| 미출석, 실패 0~2회 | 빈 값·5자리·숫자 외 문자 등 형식 오류 | 입력 오류 | 유지 | 기존 상태 유지 | 증가하지 않음 |
| 입력 잠금, 실패 3회 이상 | 정상 형식의 어떤 토큰이든 | 거절 | 유지 | 미사용이면 미사용 유지, 사용했으면 사용 완료 유지 | 더 증가하지 않음 |
| 현장 출석 | 다른 유효한 미사용 토큰 | 이미 출석으로 거절 | 기존 유형·점수·시각 유지 | 미사용 유지 | 증가하지 않음 |
| 수동 승인 | 다른 유효한 미사용 토큰 | 이미 출석으로 거절 | 기존 유형·점수·시각 유지 | 미사용 유지 | 증가하지 않음 |
| 과제 인정 | 다른 유효한 미사용 토큰 | 이미 출석으로 거절 | 기존 유형·점수·시각 유지 | 미사용 유지 | 증가하지 않음 |
| 어떤 유형이든 이미 출석 | 자신·타인이 사용한 토큰, 미발급 토큰 | 거절 | 기존 유형·점수·시각 유지 | 기존 상태 유지 | 증가하지 않음 |
| 어떤 유형이든 이미 출석 | 형식이 잘못된 토큰 | 입력 오류로 거절 | 기존 유형·점수·시각 유지 | 기존 상태 유지 | 증가하지 않음 |

추가로 알아둘 점:

- 실패 횟수는 **존재하지 않거나 이미 사용된 6자리 토큰을 미출석·미잠금 학생이 제출한 횟수**입니다. 이름 오류, 형식 오류, 이미 출석, 시작 전·종료, 요청 제한은 이 횟수를 올리지 않습니다.
- 성공해도 이전 실패 횟수를 자동으로 0으로 만들지 않습니다. 관리자의 **잠금 해제**가 0으로 되돌립니다.
- `000000`, `001234`도 실제 발급된 미사용 토큰이라면 유효합니다. 0으로 시작한다는 이유로 거절하지 않습니다.
- 학생 입력칸은 숫자 외 문자를 제거하고 최종 6자리를 제출합니다. 직접 API를 호출할 때는 토큰을 문자열로 전달해야 합니다. JSON 숫자 `123456`과 문자열 `"123456"`은 구분하며 숫자 자료형은 거절합니다.
- 학생이 본인을 확인한 뒤 관리자 조작으로 출석 상태가 바뀌어도, 토큰 제출 시점의 DB 상태로 다시 판단합니다. 학생이 제출한 출석 유형이나 화면에 남아 있는 과거 상태를 신뢰하지 않습니다.

## 4. 여러 조건이 동시에 잘못된 경우의 우선순위

학생 폼은 먼저 학번·이름과 동의를 검증하고, 통과한 경우에만 토큰 제출을 합니다. 토큰 제출 API에서는 세션·동의·요청 제한·토큰 형식을 검사한 다음, DB 안에서 **접수 중 → 학생 존재 → 이미 출석 아님 → 잠금 아님 → 미사용 토큰** 순서로 검사합니다.

따라서 출석한 학생이 5자리 토큰을 직접 API로 보내면 형식 오류가 먼저 나오고, 종료 상태에서 정상 형식 토큰을 보내면 종료 안내가 먼저 나옵니다. **표시되는 오류가 달라도 출결과 토큰을 바꾸지 않는 결과는 같습니다.** 이미 출석하면서 실패 횟수가 3인 학생도 새 출석은 거절되며 기존 출석은 유지됩니다.

## 5. 동의·세션·요청 제한과 장애

| 조건 | 결과 | 출결·토큰·토큰 실패 횟수 |
|---|---|---|
| 개인정보 미동의 | 화면 버튼 비활성, 직접 제출도 거절 | 모두 유지 |
| 세션 없음·위조·만료·로그아웃으로 폐기됨 | 본인 확인 다시 필요, 401 | 모두 유지 |
| 지나치게 많은 요청 | 잠시 대기, 429 | 모두 유지 |
| 다른 출처에서의 쓰기 요청·Origin 누락 | 거절, 403 | 모두 유지 |
| 잘못된 JSON·지원하지 않는 자료형·과도한 본문 | 요청 오류 | 모두 유지 |
| 필수 서버 키·DB 연결 미설정 | 설정 오류, 503 | 모두 유지 |
| DB 쓰기 도중 오류 | 실패, 원자적 쓰기 전체 취소 | 출결만 되거나 토큰만 쓰이는 부분 변경 없음 |

학생 세션 유효기간은 30분입니다. 출석·조회 폼은 매번 학번·이름과 동의를 제출해 세션을 발급합니다. 직접 `/api/attendance`를 호출하면 **유효한 세션의 학생**만 대상으로 하며, 본문에 다른 학번을 넣어 대상을 바꿀 수 없습니다. `/api/result` 조회는 유효한 세션으로 현재 상태를 읽고 출결이나 토큰을 바꾸지 않습니다.

학생에게 별도의 로그인이나 세션 발급 작업은 없습니다. 학번·이름·토큰을 입력하고 동의 후 출석 버튼을 한 번 누르면, 브라우저가 학생 확인 → 세션 쿠키 자동 저장 → 토큰 제출을 이어서 수행합니다. 정상 화면은 매번 새 세션을 발급하므로 오래된 세션의 만료를 학생이 수동으로 해결할 필요가 없습니다. 서로 다른 학생의 세션과 학번별 제한은 독립적입니다. 같은 IP의 학생 100명이 이 전체 과정을 동시에 수행하는 로컬 HTTP 검증도 통과했습니다. 실제 Cloudflare 원격의 100명 부하 검증은 별도입니다.

현재 학생 확인은 **학번당 60초에 5회**이며 **IP당 제한은 없습니다.** 교내 Wi-Fi처럼 같은 외부 IP를 쓰는 학생도 학번별로 독립적으로 처리합니다. 출석 폼과 조회 폼의 학생 확인은 같은 학번의 제한을 공유하며, 이름 일치·불일치 결과와 관계없이 확인 요청을 셉니다. 형식·동의 검사를 통과한 첫 요청부터 60초간 최대 5회를 허용하고 6회째부터 429를 반환합니다. 제한된 요청이 들어와도 만료 시각을 뒤로 연장하지 않습니다.

검증은 브라우저가 아닌 서버의 `/api/session`에서 수행합니다. `server/app.js`가 학번과 한도를 `server/security.js`의 `rateLimit()`에 전달하고, D1 `rate_limits` 테이블의 카운터를 원자적으로 갱신합니다. 학번은 서버 비밀키로 만든 검증값을 키로 사용합니다. 다른 기기·새로고침·다른 IP에서도 같은 학번의 한도를 공유합니다. 이전 IP 제한 기록은 더 이상 읽지 않으므로 남아 있어도 차단하지 않습니다.

미등록 학번은 저장 공간 공격을 막기 위해 별도의 최대 256개 제한 구역을 공유합니다. 등록 학생의 학번별 제한과 섞이지 않으며 같은 IP의 등록 학생을 함께 제한하지 않습니다. 실제 이름이 변경되면 해당 학생의 기존 세션은 폐기되고 새 이름으로 다시 확인해야 합니다. 이름을 그대로 재등록하는 경우 세션은 유지됩니다.

토큰 제출은 별도로 **학번당 60초에 6회**를 유지합니다. 이 두 시간 제한은 토큰 3회 실패 잠금과 별개이며, 429는 출결·토큰·실패 횟수를 변경하지 않습니다.

응답을 받기 전에 네트워크가 끊기거나 성공 후 결과를 읽어 응답하는 단계에서 오류가 난 경우는 DB 쓰기 롤백과 다릅니다. 서버에서 이미 성공했을 수도 있으므로 조회로 확인합니다. 재제출되어도 이미 출석이면 추가 토큰을 소비하지 않습니다.

## 6. 동시 요청

| 상황 | 결과 |
|---|---|
| 같은 학생이 서로 다른 미사용 토큰 두 개를 동시에 제출 | 한 번만 출석. 한 토큰만 사용하고 다른 토큰은 미사용 유지. 나머지 요청은 이미 출석으로 거절 |
| 서로 다른 학생이 같은 토큰을 동시에 제출 | 한 학생만 출석. 토큰은 그 학생이 한 번만 사용. 다른 학생의 실패 횟수는 1 증가하며 세 번째 실패라면 잠금 |
| 같은 학생이 잘못된 토큰 6개를 동시에 제출 | 토큰 판정·실패 횟수·활동을 같은 트랜잭션으로 처리. 1~2회 오류, 3회째 잠금, 이후에도 잠금. 실패는 3건만 기록 |
| 세션 검사 후 출석 쓰기 전에 로그아웃·명단 수정으로 폐기됨 | 출석 트랜잭션에서 재검사해 거절. 토큰·출결·토큰 실패 횟수 유지 |
| 같은 학생의 출석 취소가 동시에 두 번 요청됨 | 한 번만 변경·기록. 두 번째는 이미 미출석으로 거절 |
| 관리자의 취소와 학생 제출이 겹침 | DB의 원자적 작업이 실행된 순서에 따라 판단. 취소 전이면 이미 출석으로 거절하며, 취소 후라면 새로운 미사용 토큰으로 출석 가능. 이전 사용 토큰은 계속 사용 완료 |

## 7. 관리자가 상태를 바꾸는 경우

| 관리자 작업 | 출결 | 토큰 | 실패 횟수·기록 |
|---|---|---|---|
| 수동 승인·과제 인정 | 미출석 학생을 해당 유형·5점·현재 시각으로 변경. 이미 출석이면 거절 | 소비하지 않음 | 실패 횟수 유지, 승인 활동 기록 추가 |
| 미출석 처리 | 유형 `NONE`, 출석 여부 0, 점수 0, 처리 시각 없음 | 과거 사용 번호·사용자·시각 유지. 재사용 불가 | 실패 횟수와 과거 활동 유지, 취소 활동 기록 추가 |
| 잠금 해제 | 기존 출결 유지 | 기존 상태 유지 | 실패 횟수만 0으로 변경, 해제 기록 추가 |
| 토큰 메뉴의 전체 초기화 | 기존 학생 출결 유지 | 관리자가 명시적으로 토큰 사용 상태를 초기화함 | 기존 활동 유지, 작업 기록 추가 |
| 토큰 삭제 | 기존 학생 출결 유지 | 삭제한 번호는 사용할 수 없음 | 기존 활동 유지, 작업 기록 추가 |
| 운영 설정의 모두 초기화 | 명단·출결 모두 삭제, 행사 설정도 초기값 | 토큰도 삭제 | 학생 세션·활동·요청 제한 상태도 삭제 |

**미출석 처리에서 사용 토큰을 되살리는 일은 없습니다.** 기존의 별도 토큰 초기화 버튼은 관리자가 토큰 자체를 재사용하도록 명시적으로 초기화하는 기능입니다. 이미 출석한 학생은 그 경우에도 다른 토큰으로 중복 출석할 수 없습니다.

수동 승인으로 잠금된 학생을 출석 처리한 뒤 미출석으로 되돌리면 이전 실패 횟수 3회가 남습니다. 학생이 새 토큰으로 출석하려면 관리자가 잠금도 해제해야 합니다. 관리자는 출석 취소를 접수 종료 후에도 할 수 있지만 학생의 재출석에는 접수 중 상태가 필요합니다.

## 검증 범위

`tests/rules.test.mjs`는 신원 3종 × 학생 상태 8종 × 접수 상태 3종 × 토큰 7종의 **504개 조합**에서 응답, 출결 필드, 실패 횟수, 모든 토큰의 상태를 독립 메모리 DB로 비교합니다. 별도로 관리자 권한·취소·중복·동시성·롤백·선행 0 토큰·마이그레이션 보존을 테스트합니다. 브라우저에서는 취소 확인창, 미출석 표시와 새 토큰 재출석을 확인합니다.

SQLite 메모리 테스트 외에 독립 D1 로컬 에뮬레이터에서 사용 토큰·기존 출석이 있는 DB의 0003 업그레이드와 재출석을 확인했습니다. 실제 원격 DB, 실제 Access 로그인, 다수의 현장 기기가 만드는 부하는 이 검증에서 실행하지 않았습니다. 적용 절차는 [운영 문서](OPERATIONS.md#출석을-미출석으로-되돌리기)를 따릅니다.
