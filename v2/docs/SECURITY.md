# 보안 점검과 남는 위험

2026-10-27 기준. v2 서버·클라이언트·DB 제약을 검토하고 새 가상 데이터로만 검사했습니다. 원격 공격·부하 테스트, 실제 Access 로그인, 계정 설정 변경은 실행하지 않았습니다. 모든 취약점을 찾았다는 보증이나 응답 시간의 일정함을 검증한 결과는 아닙니다.

## v1에서 겪은 공격에 대한 결과

| 시도 | v2의 판단 |
|---|---|
| DB 식별자나 API 주소를 알아내 토큰 목록 읽기 | 공개 목록·개별 토큰 조회·DB 프록시 API가 없음. D1은 서버 바인딩으로만 접근 |
| 인증 없이 6자리 번호 대입 | `/api/attendance`가 401. 미사용·사용 완료·미발급 번호에 같은 응답 |
| 사용된 번호와 미발급 번호 구별 | 정상 학생의 실패 응답도 동일한 상태·코드·문구. 잠기면 모든 정상 형식 번호에 동일한 423 |
| Local Overrides로 잠금 해제·화면 수정 | 화면만 바뀜. 서버는 D1의 실패 횟수·출결·접수 상태와 서명된 세션을 재검사 |
| `trial_count: -999`, `trial_count: 0`, 역할·점수·다른 학번 추가 | 학생 API가 이 값들을 권한이나 출결 판단에 사용하지 않음 |
| 새로고침·다른 브라우저·다른 IP·새 쿠키 | 동일 학번의 DB 실패 횟수와 제한을 공유. 60초 제한이 풀려도 3회 잠금은 유지 |
| 같은 토큰 또는 학생으로 동시 제출 | DB의 현재 출석·토큰 고유 제약과 트리거가 한 번만 소비하도록 보호 |
| 이메일 헤더만 조작해 관리자 접근 | 거절. 서버가 Access JWT의 서명·발급자·AUD·만료·허용 이메일 검증 |

학생 확인은 등록 학번당 60초에 5회, 토큰 제출은 학번당 60초에 6회입니다. 유효하지 않거나 사용된 정상 형식 토큰을 3회 입력하면 DB에서 잠깁니다. 학번·이름 확인 없이 토큰만 시험하는 API는 없습니다. IP 제한·Turnstile·추가 학생 로그인은 추가하지 않았습니다.

## 이번에 발견해 보완한 부분

1. **동시 대입에서 실패 횟수 반영 지연.** 기존에는 실패한 claim 삽입과 횟수 증가가 다른 DB 요청이었습니다. DB 응답을 겹치게 한 로컬 재현에서 6개 번호가 실패 판정을 받은 뒤에야 횟수가 저장됐습니다. 토큰 판정·성공 소비 또는 실패 증가·실패 기록을 한 `DB.batch()` 트랜잭션으로 변경했습니다. 이제 6개를 동시에 보내도 실패 판정은 3회이고 이후 요청은 잠금으로 거절됩니다. 실패 활동도 실제 증가에만 기록하고 중간 오류는 전체 롤백합니다.
2. **검증 직후 폐기된 세션으로 쓰기 가능.** 세션 검사와 쓰기 사이에 로그아웃해도 진행 중 요청은 성공할 수 있었습니다. 출석 트랜잭션 안에서도 해당 학생의 세션이 아직 존재하고 유효한지 확인합니다.
3. **명단의 이름 수정 후 기존 세션 유지.** 이름이 실제로 바뀐 학생의 기존 세션을 명단 갱신과 함께 폐기합니다. 이전 이름을 확인한 요청이 수정 뒤에 새 세션을 만드는 경계도 조건부 삽입으로 막았습니다. 같은 명단을 재등록할 때는 세션을 유지합니다.
4. **잘못된 JSON 자료형 허용.** 배열이나 숫자가 문자열로 자동 변환되어 인증되는 경우를 발견했습니다. 학번·이름은 문자열로만 받도록 검증을 강화했습니다. 이것만으로 이름 확인을 우회할 수 있었던 것은 아닙니다.
5. **임의 학번에 따른 카운터 저장 공간 증가.** 존재하지 않는 학번을 계속 바꾸면 제한 테이블에 새 행을 무제한 만들 수 있었습니다. 미등록 학번만 서버 비밀키로 정한 최대 256개 구역을 공유하고, 만료된 카운터도 세션 발급 시 최대 128개씩 정리합니다. 등록 학생은 기존의 독립된 학번별 제한을 사용하므로 이 구역이나 공용 IP 때문에 차단되지 않습니다.
6. **관리자 인증 추가 검증.** JWT에 만료 시각과 이메일이 반드시 있어야 하도록 했습니다. 공격자 서명, 다른 발급자·AUD, 만료·만료 누락, 비허용 이메일, HS256 및 `alg:none` 위조를 모두 거절하는 회귀 검증을 추가했습니다.

Cloudflare는 `batch()`를 순차 실행하는 트랜잭션으로 제공하며 실패 시 전체를 되돌립니다. [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

## 남는 위험과 운영 판단

| 위험 | 현재 한계와 대응 |
|---|---|
| 학번·이름을 아는 사람의 사칭·대리 출석 | 두 정보만으로 실제 당사자인지 구별할 수 없음. 유효한 종이 토큰까지 공유하면 대리 출석 가능. 강한 신원·현장 증명에는 별도 인증이나 현장 확인이 필요 |
| 6자리 토큰의 추측 가능성 | 키가 있어야 DB를 검증할 수 있는 것과 온라인 추측 확률은 별개. 미사용 토큰이 100개면 무작위 한 번의 적중 확률은 1만 분의 1. 여러 학번·이름을 알아 300회 시도할 수 있다면 첫 적중 확률은 약 3%로 추산됨(독립 무작위 시도 가정). 더 긴 토큰은 이 위험을 낮추지만 현재 6자리 사용 방식은 유지 |
| 타인 잠금 유발 | 학번만 알아도 잘못된 이름을 보내 분당 확인 제한을 소모할 수 있음. 학번·이름을 알면 잘못된 토큰 3회로 해당 학생을 잠글 수 있음. 현장에서 명단 확인 후 관리자 잠금 해제로 대응 |
| 대량 요청으로 가용성·요금 공격 | 학번별 제한은 모든 공개 경로의 DDoS 방어가 아님. config 요청이나 잘못된 입력도 실행 자원을 사용하며, 카운터 수를 제한해도 요청 처리 비용은 남음. Cloudflare 요청·오류·D1 사용량을 관찰하고 공격 시 해당 계정의 방어 기능과 운영 절차로 대응 |
| 관리자 계정·서버 비밀값 유출 | 관리자에게는 실명·모든 토큰 열람·초기화 권한이 있음. 관리자 Access 허용 이메일을 최소화하고 계정을 보호해야 함. `SESSION_SECRET`과 `DATA_SECRET`은 서버에만 저장 |
| DB·백업 유출 | 요구사항에 따라 실명은 DB에 저장됨. 화면 마스킹은 DB·백업 유출 방어가 아님. 토큰 원문은 AES-GCM, 검증값은 서버 키를 사용하는 HMAC이지만 `DATA_SECRET`까지 유출되면 보호할 수 없음 |
| 관리자 토큰 전체 초기화 | 의도적으로 사용 토큰을 다시 배부 가능하게 만드는 기능임. 이전 종이 번호도 다시 유효해지므로 운영 중에는 경고창의 전체 범위를 확인 |

계정별 잠금은 대입을 제한하지만 타인 계정을 잠그는 서비스 거부에도 악용될 수 있습니다. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Denial of Service Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)

Origin 검사는 다른 사이트에서 브라우저를 이용하는 요청을 막기 위한 것입니다. 직접 HTTP 요청을 만드는 사람은 Origin도 지정할 수 있으므로 비밀값이나 봇 방어로 취급하지 않습니다. 학생 세션·관리자 JWT·DB 검증이 실제 권한 경계입니다. 브라우저에 내려보낸 공통 API 키를 숨기는 방식도 사용하지 않습니다.

## 검증과 적용

1. `v2`에서 로컬 검사:

   ```powershell
   npm.cmd test
   npm.cmd run lint
   npm.cmd run build
   npm.cmd run test:security:d1
   npm.cmd run test:browser
   npm.cmd audit --omit=dev
   ```

   서버 테스트 58개(규칙 504조합 포함), 브라우저 7개, lint·빌드가 통과해야 합니다. `test:security:d1`은 Functions 빌드 뒤 Wrangler의 로컬 workerd/D1 임시 DB에서 동시 대입 3회 잠금과 같은 IP 100명 정상 출석을 확인합니다. 테스트 런타임에는 코드 내 테스트 값만 주입하며 `.env`의 실제 키나 원격 바인딩·영속 DB에 연결하지 않습니다. `audit`의 알려진 운영 의존성 취약점은 점검 시 0건이었습니다. 모든 보안 문제가 없다는 의미는 아닙니다.
2. 원격 대상 확인:

   ```powershell
   npx.cmd wrangler whoami
   npx.cmd wrangler d1 list
   ```

   배포할 Pages 프로젝트와 기존 DB ID·`DB` 바인딩, 서버 비밀값, `/manage` 및 `/api/admin/*` Access 보호를 확인합니다. 로컬 키·DB를 원격에 복사하지 않습니다.
3. GitHub에 반영한 커밋을 Pages에 배포한 뒤 **원격 전용 가상 학생**으로 정상 출석·조회·3회 잠금·관리자 해제를 소량 확인합니다. 미로그인·학생 쿠키로 관리자 API가 거절되는지 확인합니다. 원격에서 무작위 대량 대입이나 실제 명단에 대한 잠금 시험은 하지 않습니다.

이번 보완에는 새 DB 스키마·서버 환경값이 필요 없습니다. 기존 출석 취소 기능의 0003 적용은 별도입니다. 원격 DB 쓰기·직접 배포·Access 설정 변경·원격 부하 검증은 이번 점검에서 수행하지 않았습니다. GitHub 푸시로 연결된 자동 배포가 시작될 수 있으므로 Pages 배포 상태는 별도로 확인합니다.

실제 요청 예시는 [학생 API 통신](STUDENT_API.md)을 참고하세요.
