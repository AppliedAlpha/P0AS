# 학생 출석 API 통신

학생은 학번·이름·토큰 입력과 동의 후 버튼을 한 번 누릅니다. 화면은 아래 두 요청을 순서대로 보냅니다. 예시는 모두 가상 정보입니다.

```text
브라우저 ── 학번·이름·동의 ──→ /api/session ──→ 명단 대조
브라우저 ←─ 학생 정보·세션 쿠키 ────────────────┘
브라우저 ── 토큰·동의 + 자동 쿠키 ─→ /api/attendance
브라우저 ←─ 출석 결과 또는 오류 ────── DB에서 최종 판단
```

## 1. 학생 확인

`POST /api/session`

```http
Content-Type: application/json
Origin: https://p0as.applied.kr
```

요청 본문(payload):

```json
{
  "studentId": "26000001",
  "name": "가상하나",
  "consent": true
}
```

서버는 동의·문자열 형식·학번별 요청 제한을 검사하고 명단의 학번·이름과 대조합니다. 등록 학생은 학번당 60초에 5회이며 공용 IP와 무관합니다. 이름이 틀려도 이 제한에 포함됩니다. 미등록 학번의 카운터는 저장 공간 보호를 위해 별도의 최대 256개 구역을 공유하며, 등록 학생의 제한과 섞이지 않습니다.

성공하면 `200 OK`와 현재 상태를 돌려줍니다. 이 단계는 출석 처리나 토큰 검증을 하지 않습니다.

```json
{
  "student": {
    "id": "26000001",
    "name_mask": "가**나",
    "trial_count": 0,
    "is_attended": 0,
    "attendance_type": "NONE",
    "score": 0,
    "attended_at": null
  }
}
```

응답 헤더에는 아래 형태의 쿠키도 있습니다. 값은 매번 생성되므로 이 예시를 실제 인증에 쓸 수는 없습니다.

```http
Set-Cookie: p0as_session=<무작위ID>.<만료시각>.<서명>; Path=/api; HttpOnly; SameSite=Strict; Max-Age=1800; Secure
```

브라우저가 쿠키를 자동 저장합니다. `HttpOnly`이므로 페이지 JavaScript가 쿠키 값을 직접 읽지 않습니다. 서버는 서명을 검증하고 DB에서 이 세션이 어느 학생의 것인지 확인합니다. 학생에게 쿠키·로그인 절차를 수동으로 요구하지 않습니다.

학번·이름 불일치와 없는 학번은 같은 `400` 오류이며 쿠키를 발급하지 않습니다. 1번 요청이 실패하면 화면은 2번 요청을 보내지 않습니다.

## 2. 토큰으로 출석

`POST /api/attendance`

```http
Content-Type: application/json
Origin: https://p0as.applied.kr
Cookie: p0as_session=<위에서 받은 값>
```

쿠키는 브라우저가 자동으로 넣습니다. 화면에서 직접 조립하는 JSON 본문은 다음 두 값뿐입니다.

```json
{
  "token": "482913",
  "consent": true
}
```

토큰은 문자열입니다. `"001234"`처럼 앞의 0도 유지합니다. 이 요청에는 학번·이름·시도 횟수·출결 상태·서버 비밀키를 보낼 필요가 없습니다. 학생은 세션으로 정합니다.

서버는 세션, 동의, 학번당 60초에 6회 제한, 토큰 6자리 형식을 검사합니다. 다음 작업은 DB 트랜잭션에서 현재 상태를 기준으로 수행합니다.

- 세션이 여전히 유효하고, 접수 중·미출석·실패 3회 미만이며 토큰이 미사용이면 출석 처리합니다.
- 출석 기록·토큰 사용·성공 활동은 함께 저장됩니다.
- 유효하지 않거나 사용된 토큰이면 실패 횟수와 활동을 함께 저장합니다. 3회째 잠깁니다.
- 이미 출석·잠금·종료·폐기 세션이면 토큰을 소비하지 않습니다.

성공 응답 `200 OK`:

```json
{
  "student": {
    "id": "26000001",
    "name_mask": "가**나",
    "trial_count": 0,
    "is_attended": 1,
    "attendance_type": "FIELD",
    "score": 5,
    "attended_at": "2026-10-27T04:00:00.000Z"
  }
}
```

응답에는 토큰 목록·토큰 원문·암호문·다른 학생 정보·서버 비밀키가 없습니다. 성공해도 기존 실패 횟수를 자동으로 0으로 만들지는 않습니다.

잘못된 토큰 첫 시도의 예시 `400 Bad Request`:

```json
{
  "error": "유효하지 않거나 사용된 토큰입니다. 종이를 확인해주세요. (1/3회)",
  "code": "INVALID_TOKEN"
}
```

| HTTP 상태 | 주요 코드 | 의미와 결과 |
|---|---|---|
| 400 | `IDENTITY_MISMATCH` | 1번 요청의 학번·이름 확인 실패. 출결·토큰 변경 없음 |
| 400 | `INVALID_INPUT` / `CONSENT_REQUIRED` | 입력 형식·동의 오류. 출결·토큰·실패 횟수 유지 |
| 400 | `INVALID_TOKEN` | 미발급·삭제·사용 토큰에 동일한 응답. 해당 학생 실패 +1, 토큰 유지 |
| 401 | `UNAUTHENTICATED` | 세션 없음·위조·만료·폐기. 출결·토큰 변경 없음 |
| 403 | `CROSS_ORIGIN` | 다른 출처 또는 Origin 없는 쓰기 요청 거절 |
| 409 | `ALREADY_ATTENDED` / `CLOSED` | 기존 출석 또는 접수 중 아님. 토큰 유지 |
| 423 | `LOCKED` | 3번째 실패 또는 이미 잠금. 토큰 유지, 실패 횟수 최대 3 |
| 429 | `RATE_LIMITED` | 학번별 시간 제한 초과. 출결·토큰·토큰 실패 횟수 유지 |
| 500 / 503 | `INTERNAL_ERROR` / `NOT_CONFIGURED` 등 | 서버·설정 오류. 응답에 내부 SQL·비밀값을 노출하지 않음 |

성공 후 응답이 도착하기 전에 연결이 끊어지면 서버에는 이미 출석이 저장되어 있을 수 있습니다. 결과 조회로 확인합니다. 재제출해도 이미 출석하면 다른 토큰을 추가 소비하지 않습니다.

## 화면을 조작하면 어떻게 되나

브라우저의 JS·요청·화면은 학생이 바꿀 수 있다고 가정합니다. `trial_count: -999`, `role: "admin"`, 다른 `studentId`를 2번 본문에 추가해도 서버는 그 값으로 DB를 갱신하거나 학생을 변경하지 않습니다. 잠금은 서버 DB에 저장되며 관리자 인증을 통과한 잠금 해제 API만 이를 0으로 되돌립니다.

자신이 입력한 토큰과 요청·응답을 개발자 도구에서 보는 것은 정상입니다. HTTPS는 외부 도청을 막지만 본인 브라우저에서 본인 입력을 숨기지는 않습니다. 이 통신을 복사해 직접 API를 호출해도 동일한 서버 검증을 통과해야 합니다. Origin 헤더만 복사해서 권한을 얻을 수 없습니다.

결과 조회 화면은 학번·이름·동의로 1번 요청만 수행해 그 응답의 현재 상태를 표시합니다. 이미 유효한 세션이 있으면 `GET /api/result`로도 본인 결과를 읽을 수 있습니다. 조회는 출결·토큰·토큰 실패 횟수를 바꾸지 않습니다.

한계와 적용 방법은 [보안 점검](SECURITY.md), 전체 판단 조합은 [출결 규칙](ATTENDANCE_RULES.md)을 참고하세요.
